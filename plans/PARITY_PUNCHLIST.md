### 2. Import Path Style

**Files affected:** All DAG files (`jupytext.py`, `run_async*.py`, `run_sequential*.py`)

**Issues:**
- Using private module paths (e.g., `.tasks.config._set_vars`) instead of public paths (`.tasks.config`)
- Missing `as func_name as func_name` pattern for explicit re-exports

**Current:**
```python
from ecoscope_workflows_core.tasks.config._set_vars import set_string_var
```

**Expected:**
```python
from ecoscope_workflows_core.tasks.config import set_string_var as set_string_var
```

#### Context for Future Agent

**To understand this issue:**
1. Look at the full import block diff in `jupytext.py`:
   ```diff

   -)
   +from ecoscope_workflows_core.tasks.config._set_vars import set_string_var
   +from ecoscope_workflows_core.tasks.config._workflow_details import set_workflow_details
   ```

2. The old compiler uses `wt-registry` to discover tasks and their "importable references"
3. The importable reference should point to the PUBLIC module path, not the private `_filename.py` path

**To find where to fix:**
1. Search for how `wt-compiler` resolves import paths for tasks
2. Look at `wt-registry` - there's likely an `importable_reference` or similar field on registered tasks
3. The registry should store public paths like `ecoscope_workflows_core.tasks.config.set_string_var`
4. Check how the old compiler generates these imports in `ecoscope_workflows_core/compiler.py`

**Key questions to answer:**
- Where does `wt-compiler` get the import path for each task?
- Does `wt-registry` store the importable reference? If so, is it storing the wrong path?
- Is there a mapping from private module paths to public re-export paths?
- How is the `as func_name as func_name` pattern generated? (This ensures explicit re-export)

**Related files in ecoscope-workflows-core/ext-ecoscope:**
